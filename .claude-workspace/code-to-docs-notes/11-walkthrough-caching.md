# Walkthrough 2 — The caching/indexing layer (`doc_index.py`)

This is the cleverest part of the project, and also the one with the most subtle correctness issues. The whole module exists for one optimization: **avoid making the LLM read every doc on every PR**.

Read it with `src/doc_index.py` open (1,485 lines, lots of helpers, but the design fits in your head once you see the two tiers).

## The problem it's solving

Without caching, every `[review-docs]` run has to:
1. Walk the docs tree (could be hundreds of `.md`/`.rst`/`.adoc` files)
2. Either send all of them to the LLM (blows context) or summarize each long file first (1 LLM call per long file, every run)
3. Then ask the LLM which are relevant

For a real docs repo with ~200 files and several thousand lines of long pages each, that's 10-30 LLM calls just for discovery, every time a developer comments on a PR. README claims this used to take ~20 minutes; with the cache it's ~4.

## The two-tier cache

```
.doc-index/                       ← lives in the docs repo
├── manifest.json                 ← per-folder index metadata + doc hashes
├── summaries_manifest.json       ← per-file summary metadata + content hashes
├── <folder>.index.md             ← AI-generated semantic index of folder (Tier 1)
├── <folder>.index.md
├── ...
└── summaries/
    ├── <path-with-dashes>.summary.md   ← AI summary of one long file (Tier 2)
    └── ...
```

Two independent caches:

- **Tier 1 — folder indexes** (`<folder>.index.md`): one per top-level docs folder. Generated by reading all files in the folder and asking the LLM to write a structured semantic index (overview, file summaries, "what code changes would require updates", key technical concepts). Used during discovery to skip whole folders that obviously don't apply.

- **Tier 2 — file summaries** (`summaries/<name>.summary.md`): one per **long** doc file (>300 lines). Used in the full-scan fallback path and inside `find_relevant_files_optimized` when looking inside an already-narrowed area.

Both are committed to the docs repo's **`main`** branch (or whatever `DOCS_BASE_BRANCH` is) so every PR shares them.

## The hot path on a cached run

`discovery.find_relevant_files_optimized(diff)` calls into doc_index in this order:

```
fetch_indexes_from_main()                # pull cache from main branch
    ↓
indexes_exist() ? build_all_indexes() : update_indexes_if_needed()
    ↓
find_relevant_areas_from_indexes(diff)   # Stage 1: which folders?
    ↓
get_files_in_areas(areas)                # list files in those folders
    ↓
[for long files] get_or_generate_summary()  # Tier 2 cache lookup
    ↓
commit_indexes_to_repo()                 # push any new indexes/summaries back
    ↓
ask_ai_for_relevant_files(diff, file_previews)   # Stage 2: which files?
```

The first stage (`find_relevant_areas_from_indexes`) is what makes this fast — it sends the LLM `N` small folder-level indexes instead of the entire doc tree.

## Step 1 — Pull cache from main (line 1076)

```python
def fetch_indexes_from_main():
    base_branch = os.environ.get("DOCS_BASE_BRANCH", "main")
    run_command_safe(["git", "fetch", "origin", base_branch], check=False)
    check_result = run_command_safe(
        ["git", "ls-tree", "-r", f"origin/{base_branch}", "--name-only"],
        check=False
    )
    if index_relative_path not in check_result.stdout:
        return False
    run_command_safe(
        ["git", "checkout", f"origin/{base_branch}", "--", index_relative_path],
        check=False
    )
```

The trick: `git checkout origin/main -- <path>` is a path-restricted checkout. It pulls **only that subtree** from main and writes it into the working tree, without switching branches. So a PR branch can grab the cache from main without leaving the PR branch.

This is why every PR sees the same cache: nobody's reading from a long-running process or a network service — they're just `git checkout`-ing it from a known location.

## Step 2 — Build or update indexes

`indexes_exist()` is a simple existence check on `.doc-index/*.index.md`. If nothing's there, `build_all_indexes()`:

```python
folders_to_build = [f for f in get_doc_folders()
                    if force or folder_needs_reindex(f, manifest)]

with ThreadPoolExecutor(max_workers=MAX_WORKERS_INDEX) as executor:  # 5 workers
    futures = {executor.submit(build_index_for_folder_with_retry, f, client): f
               for f in folders_to_build}
```

`folder_needs_reindex` compares the manifest's stored `doc_hashes` for that folder to the current SHA256 of every file in the folder. **Hash-based invalidation, no timestamps.** Means concurrent PR runs can both rebuild the same index without stepping on each other — they'll write the same content.

### Inside `build_index_for_folder` (line 318)

Two paths based on budget:

```python
total_content_size = sum(... for d in docs_content)
if total_content_size + prompt_overhead <= budget:
    # Single call with full content
    ...
else:
    # Batch and merge
    batches = _batch_docs_by_budget(docs_content, budget, prompt_overhead)
    for batch in batches:
        partial = client.chat.completions.create(...)
        partial_indexes.append(partial)
    # Then ask the LLM to merge the partials into one
    merged = client.chat.completions.create(messages=[{"role": "user", "content": merge_prompt}])
```

The merge step (line 420) is its own LLM call that takes the partial indexes and produces one unified document with no duplicate sections. If a folder has so many docs that even merging fails, the fallback at line 462 is to return the concatenated raw partials — a degraded but workable index.

`_batch_docs_by_budget` (line 264) is worth a careful read: it splits per file, and if a **single file** is larger than the available budget, it truncates that one file to fit in its own batch. So no file is silently dropped, but a giant one might be partially summarized.

### The index prompt (line 233)

```
# {folder.upper()} Documentation Index
## Overview
## Files Summary
## Code Changes That Would Require Documentation Updates
## Key Technical Concepts
## Related Components
```

The third section is the load-bearing one — it explicitly tells the LLM to enumerate "what code changes would require updating these docs." That's what the Stage 1 lookup later matches against the actual diff. Treat it as the structured **embedding-by-LLM** of the folder, where "embedding" is plain English the model can re-read.

## Step 3 — Stage 1: pick folders (line 843)

```python
def find_relevant_areas_from_indexes(diff, client=None):
    indexes = load_all_indexes()
    if not indexes:
        return None    # signal full-scan fallback

    BATCH_SIZE = 5
    for batch_idx in range(0, len(all_folders), BATCH_SIZE):
        batch_folders = all_folders[batch_idx : batch_idx + BATCH_SIZE]
        # Build prompt with 5 folder indexes + the diff
        prompt = prompt_template.replace("{DIFF_PLACEHOLDER}", truncated_diff)
        batch_relevant = _process_area_batch(client, prompt, ...)
```

Why batches of 5: keeps per-batch prompts small (each folder index is ~1-3K chars) so the LLM can give each folder real attention rather than skimming. Same idea as `MAX_FILES_PER_BATCH = 10` in discovery — smaller batches → better recall.

### The area-selection prompt (line 887)

```
START WITH THE ASSUMPTION: No documentation needs updating. This is true for most code changes.
Your job is to find EXCEPTIONS to this rule - cases where docs would become WRONG.

BEFORE selecting ANY folder, you MUST be able to answer YES to ALL of these:
1. Based on the index, does this folder document behavior that this code change DIRECTLY modifies?
2. Would the documented instructions/information become WRONG after this change?
3. Can I identify from the index summary WHAT SPECIFICALLY would become incorrect?
...
- If folders need updates: ["folder-1","folder-2"]
- If NO folders need updates: []
```

Same fight-against-over-selection energy as the discovery prompt in walkthrough 1. The contract is JSON: `[]` or `["folder-name", ...]`.

### Parsing the model's output (line 991)

```python
# Clean up response - remove markdown code blocks if present
if result_text.startswith("```"):
    result_text = result_text.split("\n", 1)[1]
if result_text.endswith("```"):
    result_text = result_text.rsplit("\n", 1)[0]

# Extract JSON array from response - model sometimes wraps it in extra text
json_match = re.search(r'\[.*?\]', result_text, re.DOTALL)
if json_match:
    result_text = json_match.group(0)

relevant_areas = json.loads(result_text)
# Filter to only include folders from this batch
relevant_areas = [f for f in relevant_areas if f in batch_folders]
```

Three layers of model-output defense:
1. Strip code fences (LLMs love to wrap JSON in ` ```json ` blocks)
2. Regex out the first JSON array in case there's prose around it
3. Filter the result against the batch's known folder names — hallucinations are silently dropped

This pattern shows up several times in the codebase. Worth borrowing.

Empty response retry behavior is interesting (line 979): after `max_retries`, an empty response is treated as `[]` rather than an error. Trade-off: occasional false negatives (some doc updates missed) vs. occasional false positives (action fails on a transient empty completion). Maintainer chose the former.

### The sentinel return values

`find_relevant_areas_from_indexes` has three meaningful return values:

| Return | Meaning | Caller does |
|---|---|---|
| `None` | No indexes exist, or AI explicitly requested full scan | Fall back to full scan (walks all docs) |
| `[]` | Indexes exist, AI says nothing matches | Done, post "no updates needed" comment |
| `[folder, ...]` | Folders to drill into | Proceed to Stage 2 |

That `None` vs `[]` distinction is load-bearing — same convention used in `find_relevant_files_optimized`.

## Step 4 — Stage 2: pick files within those folders

After Stage 1, control returns to `discovery.py`. `get_files_in_areas(relevant_areas)` lists every doc file inside the chosen folders, plus any root-level docs (line 1067 — "These are often important overview/index docs"). Then for each long file (>300 lines), the Tier 2 summary cache kicks in.

## Tier 2 — the file summary cache (lines 1156+)

```
.doc-index/summaries_manifest.json:
{
  "version": "1.0",
  "files": {
    "admin/config.rst": {
      "hash": "a3f...",
      "generated": "2026-03-12T10:11:00",
      "summary_file": "admin-config.rst.summary.md"
    },
    ...
  }
}
```

Key API:

```python
def get_or_generate_summary(file_path, content, generate_func):
    cached = load_cached_summary(file_path)
    if cached:
        return cached
    summary = generate_func(file_path, content)
    if summary:
        save_summary(file_path, summary)
    return summary
```

`load_cached_summary` (line 1206) checks the manifest, hashes the current file, compares to the stored hash. Mismatch → cache miss → regenerate. So as long as the doc file's bytes haven't changed, the same summary is reused across every PR.

`save_summary` writes the summary file, then updates the manifest **under a thread lock** (line 1272):

```python
with _manifest_lock:
    manifest = load_summaries_manifest(docs_root)
    ...
    save_summaries_manifest(manifest, docs_root)
```

This is the only mutex in the whole project. It's needed because `discovery.find_relevant_files_optimized` parallelizes summary generation with a `ThreadPoolExecutor(max_workers=5)`. Without the lock, two threads finishing at the same time race on the JSON read-modify-write and either lose entries or corrupt the file. (`load_summaries_manifest` has a try/except for corrupted JSON on line 1180 that silently starts fresh — that's the recovery path for racing with anything that isn't holding this lock, including a different process.)

## Step 5 — Commit back to main (line 636, the hardest function)

`commit_indexes_to_repo` exists because **the cache only helps if it persists**. Each PR run that generates new indexes or summaries should push them so the next PR doesn't redo the work. But we might be on a PR branch, the main branch might have moved, and two PRs running concurrently might generate the same summary.

The function handles four sub-cases. Read this section slowly — the logic is dense.

### Sub-case A: branch is up-to-date with main

```python
merge_base_result = run_command_safe(["git", "merge-base", "HEAD", f"origin/{base_branch}"], check=False)
main_head_result = run_command_safe(["git", "rev-parse", f"origin/{base_branch}"], check=False)
branch_up_to_date = (merge_base == main_head)
```

If `merge-base(HEAD, origin/main) == origin/main`, then `origin/main` is an ancestor of HEAD — equivalently, our branch is fully caught up. Safe to push the whole `.doc-index/` without overwriting anything newer on main.

### Sub-case B: branch is stale, content is indexes

```python
if "indexes" in content_type:
    # For folder indexes: skip entirely (could overwrite newer indexes on main)
    print("Skipping index push to avoid overwriting newer indexes on {base_branch}")
    if "summaries" not in content_type:
        return False
    content_type = "summaries"
```

A stale PR branch's regenerated folder index is **based on stale doc content**. If we push it to main, we'd undo whatever newer index someone else committed. So indexes are dropped silently. The local copy still gets used for this run — it's just not committed back.

### Sub-case C: branch is stale, content is summaries → `get_safe_summaries_to_push` (line 1409)

For summaries it's more nuanced. A summary for a doc that **hasn't changed since main** is still valid even on a stale branch.

```python
def get_safe_summaries_to_push(base_branch="main"):
    local_manifest = load_summaries_manifest(docs_root)
    main_manifest = load_manifest_from_main(base_branch)

    for doc_path, info in local_manifest.get("files", {}).items():
        # Skip if already on main with same hash
        if doc_path in main_files and main_files[doc_path]["hash"] == info["hash"]:
            continue
        # Push only if the doc itself matches main
        if doc_matches_main(doc_path, base_branch):
            safe_summaries.append(...)
```

`doc_matches_main` (line 1331) does `git show origin/main:<doc_path>`, hashes the result, and compares to the local file's hash. If they match, then "summary derived from this doc bytes" is true on main too — safe to push.

Edge case: if the file doesn't exist on main at all (line 1369), `doc_matches_main` returns `True` — new files are always safe to push their summaries.

### Sub-case D: switching to main branch to push (line 769)

Even if the content is safe, you can't just `git push origin HEAD:main` from a PR branch — GitHub will reject it (non-fast-forward or branch protection). So the function does this dance:

```python
# Save .doc-index BEFORE switching branches
temp_dir = tempfile.mkdtemp()
shutil.copytree(index_full_path, temp_index_path)

run_command_safe(["git", "stash", "--include-untracked"], check=False)
run_command_safe(["git", "checkout", "-B", base_branch, f"origin/{base_branch}"], check=True)

# Restore our saved .doc-index (overwrites main's version with our updated version)
if index_full_path.exists():
    shutil.rmtree(index_full_path)
shutil.copytree(temp_index_path, index_full_path)

# Add files, commit, push
...

# Always return to original branch and restore stash
finally:
    run_command_safe(["git", "checkout", current_branch], check=False)
    run_command_safe(["git", "stash", "pop"], check=False)
    shutil.rmtree(temp_dir, ignore_errors=True)
```

In words:
1. Copy `.doc-index/` to a tempdir.
2. Stash everything else (the PR's actual changes if any).
3. Checkout main (forcibly — `-B main origin/main`).
4. Overwrite main's `.doc-index/` with our copy.
5. Commit & push.
6. Go back to the PR branch and pop the stash.

The `finally` block is non-trivial — if the push fails halfway, we still need to be back on the PR branch with our changes restored. This is the "complex branch-switching" mentioned in `01-architecture.md`'s fragility section.

Failure modes the maintainer accepted:
- If `git stash pop` conflicts (rare, but possible if the checkout left changes that overlap), the stash is left in `git stash list` and the user has to manually recover. No notification.
- If `shutil.rmtree(temp_dir, ignore_errors=True)` actually has errors, the tempdir leaks.
- If the action gets killed mid-commit, the PR branch may be left on `main` with a half-applied state. Re-running fixes it but it looks scary.

## The .doc-index/ commit happens at a specific point

Look back at `discovery.find_relevant_files_optimized` (lines 426–434):

```python
if indexes_changed or summaries_generated:
    content_parts = []
    if indexes_changed:
        content_parts.append("indexes")
    if summaries_generated:
        content_parts.append("summaries")
    content_label = " and ".join(content_parts)
    commit_indexes_to_repo(content_type=content_label)
```

Commit happens **before** generation runs, not at the end of the whole flow. Reason: discovery is the only consumer of the cache. Once discovery has its list, the indexes have already paid for themselves; pushing them earlier maximizes the chance other concurrent PRs see them.

The combined label (`"indexes and summaries"`) is what drives the selective behavior inside `commit_indexes_to_repo`: if both indexes and summaries are new but the branch is stale, only the safe summaries get pushed.

## Mental model

If you remember nothing else:

1. **Two tiers**: folder indexes (Tier 1) shrink the search space; file summaries (Tier 2) shrink the per-file token cost.
2. **Everything is content-addressed by SHA256**. No timestamps, no version bumps. If the file bytes match the stored hash, the cache hit is correct.
3. **The cache is committed to the docs repo's main branch**. There is no other persistence layer. `git fetch + git checkout origin/main -- <path>` is how a PR branch reads it.
4. **The commit-back path is paranoid by design** — it checks branch staleness, splits content into "safe to push" and "unsafe to push," and physically copies the `.doc-index/` over to main via tempdir.
5. **One mutex** in the whole project: `_manifest_lock` guards the summaries manifest because parallel summary generation otherwise races on the JSON.
6. **`None` vs `[]` is meaningful** in the area-finder. Both mean "no work for stage 2," but only `None` falls back to full-scan.

## Sharp edges worth knowing before you touch this file

- **`get_or_generate_summary` returns a fallback on error**: discovery.py:402 catches the failure and uses raw file content as the "summary." That gets pushed downstream and could blow context budgets for very long files. Not ideal, not currently fixed.
- **`load_summaries_manifest` swallows JSON errors silently** (line 1180): manifest corruption resets the cache. Hard to debug if you wonder why summaries keep regenerating.
- **`load_cached_summary._debug_shown` is a function attribute used as state** (line 1225): innocent-looking idiom for one-shot logging, but easy to miss when reading.
- **The selective push relies on `load_manifest_from_main` succeeding**: if the docs repo is private and `gh` auth isn't set up correctly, the comparison silently falls back to `{}` (line 1406), which makes everything look "new" and push the lot. Probably fine in practice but worth knowing.
- **No file-level summary in `find_relevant_files_optimized` if the file is ≤300 lines**: short files always get full content. The 300-line threshold (`if line_count > 300:` in `discovery.py:118` and `:372`) is hardcoded and shared between the two paths, but the duplication means changing one might miss the other.

## Where this connects back to the architecture

- `discovery.find_relevant_files_optimized` is the only caller of `find_relevant_areas_from_indexes`, `get_files_in_areas`, `get_or_generate_summary`, and `commit_indexes_to_repo`.
- `suggest_docs.py --build-index` (line 60) is a CLI entry point that just runs `build_all_indexes(force=True)` and exits. This is what you'd run from a one-off `actions/checkout` + custom workflow step to pre-warm the cache before opening the first PR with the action enabled.
- The README's "~20 min → ~4 min on large projects" claim hinges entirely on this module. If you're profiling the action on a slow run, the suspect is almost always `build_all_indexes` taking too long because the LLM is slow on big folders, or `commit_indexes_to_repo` hanging on a stuck `git push`.
